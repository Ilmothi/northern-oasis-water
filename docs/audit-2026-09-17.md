# System audit — 2026-09-17

Northern Water Company Ltd (OASIS Springs) business management system.

**Scope.** Everything since `docs/audit-2026-09-08.md`: migration `028`, the
seven commits that touched `src/App.jsx` in PRs #44–#55, and a re-check of every
finding the last audit left open. Line references are against `f1cd85c`
(`origin/main`).

**Baseline health.** `npm run build` and `npm run lint` both pass clean.

**Method note.** No live-database access, so nothing here is settled by probing.
Where a question needs the database it is stated as a query to run. One finding
below was instead settled by *simulation* — the arithmetic in question is pure,
so it can be reproduced exactly without production data, and it was.

**Outcome — eight findings.** One high, two medium, five low.

**The last audit's list has largely been worked through.** Seven of its ten
findings are closed, including finding 1, the payroll gap that had been open and
unchanged for five weeks. `028` is the strongest migration in this directory:
the amounts, the payees and the runs a payout covers are all derived
server-side, both gates fail closed, and the header states its own ordering
constraint. The client half is complete — keys, in-flight flags, disabled
buttons, replay-aware state merging.

**The high finding is a consequence of that work, not of its absence.** `028`
cross-checks the client's total against its own derivation to the cent. Casual
pay is rounded per employee server-side and summed unrounded client-side, so the
two legitimately differ by up to half a cent per payee — while the tolerance is
a flat cent. Simulated over realistic payouts, **about half are refused**, with
a message telling the operator to reload, which cannot help. This is live in
production as of 2026-09-15 and it blocks the casual payroll path.

**The other theme is that `028` closed the write path and left the reverse
path.** Deleting a payroll expense still unwinds the payroll rows and the
production-run flags in N+2 unguarded, non-atomic round trips — the shape `028`
was written to eliminate.

**Status key.** OPEN = needs work. RESOLVED = settled by this audit.

## High

### 1. The casual payout cross-check refuses about half of all legitimate payouts — OPEN, live since 2026-09-15

`record_casual_payout` derives the payout total itself and refuses the write if
the client's figure differs by more than a cent (`028:568`):

```sql
if v_claimed is not null and abs(v_claimed - v_total) > 0.01 then
  raise exception 'record_casual_payout: this screen shows % but the production
    records give % for %. Reload and try again.', v_claimed, v_total, v_label;
end if;
```

The two figures are computed differently, and the difference is not noise — it
is structural:

| | Rounding | Where |
|---|---|---|
| Server | `round(sum(cartons) × rate, 2)` **per employee**, then summed | `028:306` |
| Client | `sum(share × rate)` unrounded across all employees, then `.toFixed(2)` once | `src/App.jsx:1388` |

Each payee therefore contributes up to ±0.005 of independent rounding error, and
the totals diverge by up to `0.005 × (number of payees)`. **The tolerance does
not scale with the number of payees; it is a flat 0.01.** Three payees is the
most that fits inside it, and only in the best case.

**This was simulated, not assumed.** Modelling the two calculations exactly:

| Scenario | Client | Server | Difference | Result |
|---|---|---|---|---|
| 6 casuals, one 100-carton run, rate 10 | 1 000.00 | 1 000.02 | 0.02 | **refused** |
| 7 casuals, one 100-carton run, rate 50 | 5 000.00 | 5 000.03 | 0.03 | **refused** |
| 9 casuals, one 200-carton run, rate 15 | 3 000.00 | 2 999.97 | 0.03 | **refused** |
| 3 casuals, one 100-carton run, rate 10 | 1 000.00 | 999.99 | 0.01 | accepted (just) |

Over 5 000 randomised week-long payouts — 3 to 10 casuals in the pool, six
production days, 70 % attendance, 40–200 cartons a run, rate drawn from
{5, 10, 15, 20, 25, 50} — **48.9 % exceeded the tolerance and would be
refused.** The clean cases are the ones where the carton count divides evenly by
the head count; those are the exception, not the rule.

**What the operator sees.** The HR Casual Pay view shows a total (`7486`), they
confirm it in a dialog, and the save fails with *"this screen shows 1,000.00 but
the production records give 1,000.02 … Reload and try again."* Reloading changes
nothing: the divergence is in the arithmetic, not in stale state. The payout
cannot be recorded through the UI at all, and the message points the operator at
the wrong cause — it reads as a data problem, which invites someone to go
"correcting" production logs that are perfectly correct.

**Nothing is mis-recorded.** The function refuses before it writes, so no money
moves and no half-state is created. The damage is a blocked payroll path and a
misleading diagnosis.

**Why it was missed.** `028`'s header identifies the rounding difference exactly
— *"casual pay is now rounded to the cent PER EMPLOYEE and the expense is the
sum of those rounded rows. The client totals unrounded floats"* — and then
concludes *"the two agree to the cent for every realistic payout, and where they
would not, the tolerance below absorbs it."* The observation is right and the
conclusion is wrong: the error is per-payee, so it accumulates, and one cent
absorbs at most two payees' worth.

**Fix — make the client round the same way.** It already holds the per-employee
figures, so this is one line at `1388`:

```js
const total = rows.reduce((s, e) => s + Math.round(pay[e.id].pay * 100) / 100, 0);
```

That is exactly the server's round-per-employee-then-sum, so the two agree to
the cent by construction and the tolerance goes back to catching what it is for
— genuinely stale state. Apply the same change at `7486` so the figure on screen
is the figure that will be recorded.

Widening the tolerance instead (`greatest(0.01, 0.005 * n_payees + 0.01)`) also
works and needs no deploy, but it loosens a control rather than fixing the
mismatch. Prefer the client fix; use the tolerance only as a stop-gap if a
payout is due before the next deploy.

**Verify before merging** by recording one real payout with at least four
casuals in range.

## Medium

### 2. Deleting a payroll expense still unwinds it in N+2 unguarded round trips — OPEN

`028` made the payroll *write* atomic. `handleDeleteExpense` (`3403`) is the
path that reverses it, and it is untouched — still the pre-`028` shape:

1. `supabase.from('expenses').delete()` (`3406`) — no `withTimeout`
2. `supabase.from('payroll_payments').delete().eq('expense_id', id)` (`3425`) —
   no `withTimeout`
3. a `for` loop of one `production_logs` update per run (`3431`–`3437`) — no
   `withTimeout`, one round trip each

There is no transaction and no foreign key doing this for us: no migration in
this directory declares an FK on `payroll_payments.expense_id` or
`production_logs.casual_expense_id`. The function's own alerts admit the failure
modes — *"Expense deleted, but its payroll records could not be removed"*,
*"Expense deleted, but a production run could not be returned to Pay Due"*.

This is the same shape `028`'s header describes as the thing it exists to
eliminate, running in the opposite direction.

**Two specific defects inside it, beyond the missing transaction:**

- **The local state update is optimistic, and the function's own header says it
  is not.** The comment at `3398` reads *"Persist-first: the expense row is
  deleted (and the result checked) before any local change."* True for the
  expense. But `setPayrollPayments(...)` at `3424` runs **before** the delete at
  `3425`, and the `setState` at `3440` applies `updatedLogs` regardless of
  whether any of the per-run updates succeeded. A failed unwind leaves the
  browser showing a state the database does not have.
- **A partial unwind now collides with `028`'s own guards.** If the payroll rows
  survive, the browser shows the salary unpaid, the operator records it again,
  and `028`'s unique index refuses with *"a salary for X has already been
  recorded"* — correct, but baffling in front of a screen showing "Record
  Payment". If a run fails to un-flag, the client's payout total includes it and
  the server's does not, so the next payout trips finding 1's cross-check for a
  second, unrelated reason.

**Impact is bounded but real.** The guards mean a duplicate cannot be *written*;
what is at risk is the browser and the database disagreeing about what was paid,
with no message that explains it.

**Fix:** a `delete_payroll_expense(p_expense_id)` RPC in the next migration —
admin-gated with `is distinct from`, doing all three steps in one transaction and
returning the affected ids, with the client wrapping it in `withTimeout` and
applying state only from the result. The same shape as `delete_payment_batch`.
As an interim, wrapping the three calls in `withTimeout` and moving
`setPayrollPayments` after its delete costs a few lines and removes the
optimistic half.

### 3. `record_casual_payout` reads the run set twice, at two different snapshots — OPEN

`028`'s header states: *"`casual_runs_in_range` is now the single definition, and
both the pay calculation and the flag update read it, so the runs paid for and
the runs marked paid cannot come apart."* The definition is single; the **read**
is not.

```sql
v_run_ids := array(select run_id from casual_runs_in_range(v_start, v_end) …);  -- 548
perform 1 from production_logs where id = any(v_run_ids) for update;            -- 554
…
select coalesce(sum(pay), 0) into v_total from casual_pay_for_range(…);         -- 561
…
update production_logs set casual_paid = true … where id = any(v_run_ids);      -- 614
```

`casual_pay_for_range` calls `casual_runs_in_range(p_start, p_end)` again
internally (`028:299`). Under READ COMMITTED each statement takes a fresh
snapshot, so a production run committed between lines 548 and 561 — in range,
with casuals and a non-zero carton count — **is included in `v_total` but is not
in `v_run_ids`.** It is not locked at 556 and not flagged at 614.

The run is therefore paid for and still shows as "Pay Due", so it is paid again
in the next payout. That is a genuine double payment, and it is precisely the
outcome the file was written to make unreachable.

**The window is narrow** — the gap between two statements in one transaction,
needing a production run to be logged inside it — and finding 1's cross-check
accidentally backstops it, since the extra run's pay would blow past the
tolerance. But the backstop is incidental: it is skipped entirely when
`v_claimed` is null, which any direct API call produces.

**Fix:** compute the pay from the locked set, not from a second range query.
Give `casual_pay_for_range` a `bigint[]` overload taking `v_run_ids`, or inline
the split over `v_run_ids`. Either makes the header's claim true. Do it in the
same migration as finding 2.

### 7. The production run card prices settled casual pay at today's rate — OPEN

`payPerCasual` (`8044`) is `sharePerCasual × casualRate`, where `casualRate` is
the **current** value from `cost_settings`. The card displays it next to a badge
reading *"Casual pay settled — included in a recorded payout"* (`8120`–`8122`).

For a run already paid, the figure shown is not what was paid; it is what the
same work would be worth at today's rate. The two agree only until the rate
changes, and the rate is editable in Cost Settings.

Display-only — it writes nothing and no report reads it. But it sits under a
label asserting the payment is history, which is the one context where a
recomputed figure reads as a record. `payroll_payments` holds the actual amount,
keyed by `employee_id` and a `period_label` that covers the run's date. Prefer
the recorded figure when the run is settled; keep the estimate for a run that is
not.

### 8. The run card's cost concealment is not backed by anything — OPEN

`showCosts` (`8029`) hides run value and casual pay from sales users, with the
comment that it draws *"the same line Cost Settings already draws."* It does
not. `cost_settings_select` is `using (auth.uid() is not null)`
(`001:397`–`399`) — every authenticated user may read it — and the client loads
it unconditionally at login (`1069`), setting `casualRate` for all roles
(`1076`). Carton costs and the casual rate are already in every sales user's
browser.

`001` grants that read deliberately (*"carton costs are displayed across
roles"*), so this is not a policy defect. It is the UI-only concealment CLAUDE.md
warns against, and the code comment overstates what it achieves. Either accept
it as cosmetic and say so in the comment, or move cost reads behind a role check
in RLS and stop shipping the blob to sales clients.

`028` grants `execute` on `casual_pay_for_range` to `authenticated` on the same
reasoning (*"they expose nothing a manager cannot already see"*). That is true
of managers; the grant is to every authenticated role. Harmless given the above,
but the justification and the grant are not the same width.

## Verified sound

Traced and found correct. Recorded so the next audit need not re-derive it.

- **`028` does not restate the P&L.** The expense it writes is byte-for-byte the
  shape the old client wrote — `category: 'operating'`, `subcategory: 'Salary'`
  / `'Casual Labour'`, `advance_employee_id: null` — checked against the removed
  code in `5926a43`. Treatment resolves from `subcategory` through
  `EXPENSE_TREATMENT` (`2071`), both names are `'operating'` in `EXPENSE_TYPES`
  (`291`, `310`), and no historical figure moves.
- **No double-counting of casual labour.** COGS is cartons sold × carton cost,
  and carton cost is raw materials only (`2044`). `generateProductionReport`'s
  `casualCost` (`2302`) is labelled information-only and posts nothing. Casual
  Labour reaches the P&L exactly once, as an operating expense.
- **Both `028` gates fail closed.** `v_role is distinct from 'admin'` in both
  functions (`369`, `530`), not `<>` — the null-role trap `010` fell into, named
  in the file's own header before being avoided. `search_path` is pinned on all
  four functions.
- **The salary cross-check is safe.** One value rounded once
  (`round(rate - advances, 2)`, `028:396`) against the client's unrounded
  `Number(emp.rate) - advances` (`7414`) can differ by at most 0.005, inside the
  0.01 tolerance. Finding 1 is specific to the casual path, where the error is
  per-payee and accumulates.
- **The advance definition matches on both sides.** Server:
  `advance_employee_id = emp and to_char(date::date,'YYYY-MM') = month`
  (`028:391`). Client `getAdvancesForEmployee` (`1244`): same column, same
  `slice(0,7)` month. The Salary expense itself is written with a null
  `advance_employee_id`, so it cannot count against next month's net.
- **`applyPayrollResult` (`1284`) is replay-safe.** Rows are merged by id through
  a `Map` rather than appended, so a retry the database correctly refused to
  record twice cannot appear twice in the browser either. The payroll buttons
  carry `runSave` for the in-flight ref, `disabled={saving}`, and a per-key
  `recordingPayroll` label — the pattern `applyingCredit` established.
- **Every `supabase.rpc(` call in the file is now wrapped in `withTimeout`** —
  26 call sites, checked one by one. Finding 6 of the last audit is closed for
  RPCs. What remains unwrapped are table-API writes: employees (`1465`, `1473`,
  `1487`), cost settings (`1501`, `1515`), the stock-adjustment log (`1610`),
  purchases delete (`1758`), customers delete (`4748`), and the expense delete
  path of finding 2.
- **`deleteFailureMessage` is a separate helper for a real reason.** A hung save
  risks a duplicate, so the advice must be "do not enter it twice"; a hung delete
  cannot happen twice, so the advice is "go and look, asking again is safe."
  Opposite advice, correctly not merged into one flag.
- **The aging fix is right.** `daysOverdue` now anchors on the earlier of the
  oldest unpaid sale and the oldest debt-*deepening* adjustment (`1804`–`1811`).
  Only `amount < 0` anchors, which is correct — a positive adjustment reduces
  debt and is not something to age. `adjustmentsFor` (`624`) does sort
  oldest-first with an id tiebreak, so the `.find()` is sound, and ISO dates make
  the plain string sort chronological.
- **The three-term reconciliation mirrors the function exactly.**
  `docs/balance-reconciliation.sql` block A uses the same three terms as
  `recompute_customer_balance` (`027:322`–`350`), in the same signs. Blocks A, B
  and C were all run against production on 2026-09-16 and recorded in the file.
- **No client code re-derives a balance.** Every consumer reads `c.balance`; the
  only client-side term arithmetic is `adjustmentsTotal` (`632`), which exists to
  *explain* the stored figure in the customer card and the statement, not to
  replace it.
- **`028`'s salary `period_end` change is inert.** It now writes the true month
  end where the old client wrote `-28`. Nothing reads `period_start` or
  `period_end` anywhere in `src/App.jsx` — a grep returns no hits — so the two
  shapes coexist harmlessly in history.
- **The `FOR UPDATE` lock in `record_casual_payout` does work for the case it
  was written for.** Two concurrent payouts over overlapping ranges: the second
  blocks at `554`, then re-reads at `556` under a fresh READ COMMITTED snapshot
  and finds the runs flagged, and raises. Finding 3 is a different race, between
  two reads rather than two payouts.
