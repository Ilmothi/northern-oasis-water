# System audit — 2026-09-08

Northern Water Company Ltd (OASIS Springs) business management system.

**Scope.** Everything since `docs/audit-2026-08-08.md`: migrations `024`–`027`,
the client changes in PRs #37–#43, the unmerged `delivery-note` branch, and a
re-check of the four findings that audit left open. Line references are against
`e5bcbc9` (`delivery-note`, 3 commits ahead of `main`).

**Baseline health.** `npm run build` and `npm run lint` both pass clean.

**Method note.** This audit had no live-database access, so unlike 2026-08-08 it
settles nothing by probing. Where a question needs the database, it is stated as
a query to run rather than answered. What it does instead is check the *written
record* against the *files*, which turned up two disagreements — one of them in
the migration ledger, which is the thing the whole apply process trusts.

**Outcome — ten findings.** One high (payroll, unchanged from last month), five
medium, four low. The money-write path itself continues to be in good shape:
`024`–`027` are careful, well-documented work and the `027` client half is
complete. The weaknesses are now concentrated in two places — the one money path
that was never brought up to the standard of the others, and the records that
describe the database.

**Status key.** OPEN = needs work. RESOLVED = settled by this audit.

## High

### 1. Payroll is still the only unguarded money path — OPEN, unchanged for a month

Finding 1 of the 2026-08-08 audit, re-checked line by line. **Nothing has
changed.** Both handlers are exactly as they were:

- `recordSalaryPayment` (`src/App.jsx:1209`), fired by a plain button at `7248`
- `recordCasualPayment` (`src/App.jsx:1251`), fired by a plain button at `7320`

Neither is wrapped in `runSave` (`711`), neither is wrapped in `withTimeout`
(`728`), neither button carries `disabled`, and neither record type carries a
`client_key`. Every other save in the app funnels through the modal's one Save
button (`9398`) and is covered; these two do not go near it.

**There is still no unique constraint on `payroll_payments`.** A grep for
`create unique index` across all 28 migration files returns only the
`client_key` indexes from `021` and `027`. Nothing at the database refuses a
second payroll row.

The failure mode is unchanged and worth restating because it is the part that
makes this worse than an ordinary double-tap: the salary path is two sequential
writes with no transaction — the Salary expense (`1229`) then the payroll row
(`1238`). If the second fails the user is told *"Expense saved but the payroll
record failed"* (`1241`), and because no payroll row exists, `isSalaryPaid`
(`1203`) returns false and the UI offers **"Record Payment" again**. Retrying
produces a second Salary expense in the P&L for one salary.
`recordCasualPayment` has the same shape over more steps and its own code
already says so (`1310`).

**Impact:** duplicated Salary and Casual Labour expenses inflate operating costs
in the P&L; duplicated `payroll_payments` rows misstate what staff were paid.

**Fix, in order of value** (unchanged from last month):

1. A unique index on `payroll_payments (type, employee_id, period_label)`. This
   is the real enforcement and it is a few lines. Casual rows already carry a
   stable `period_label` — `"<start> to <end>"`, built at `1281` — so the index
   works for both types as written.
2. Route both handlers through `runSave` and `withTimeout`.
3. Make each an atomic RPC following `015`/`016`. Only this closes the
   half-committed expense.

A month of no change is itself information: this is the item that keeps being
deferred because it sits outside the modal that made everything else easy to
fix. Step 1 does not require touching the client at all.

### 3. Aging Debtors dates adjustment-only debt as brand new — FIXED 2026-09-16 (moves the age buckets — see below)

`generateAgingDebtorsReport` (`1659`) takes each debtor's `debt` from
`Math.abs(c.balance)` — correctly, so the adjustment term is included — but
derives `daysOverdue` (`1667`–`1675`) from **the oldest unpaid sale only**:

```js
const unpaidSales = state.sales
  .filter(s => s.customerId === c.id && (s.paid || 0) < s.total)
  .sort((a, b) => new Date(a.date) - new Date(b.date));

let daysOverdue = 0;
if (unpaidSales.length > 0) { /* … */ }
```

The Loglogo corrections are the case that breaks this. `027` exists precisely
because *"the per-invoice detail behind them is not [known], and cannot be
reconstructed reliably two months on"* — so those debts are carried as an
opening-balance adjustment with **no unpaid sale behind them**. `unpaidSales` is
empty, the `if` is skipped, and `daysOverdue` stays `0`.

**A June book debt therefore appears in the Aging report as 0 days overdue —
current.** The amount is right and the total is right; only the age is wrong,
and it is wrong in the flattering direction. Ageing the debt is the entire
purpose of the report.

The adjustment already carries the date needed to fix this: the form collects it
(`4304`), `027`'s payload example back-dates it (`"date": "2026-06-30"`), and the
column is `date not null default current_date`.

**Fix:** take the oldest date across unpaid sales *and* debt-deepening
adjustments. `adjustmentsFor` already returns them oldest-first:

```js
const oldestAdj = adjustmentsFor(c.id).find(a => a.amount < 0);
const anchors = [unpaidSales[0]?.date, oldestAdj?.date].filter(Boolean).sort();
const daysOverdue = anchors.length
  ? Math.max(0, Math.floor((today - new Date(anchors[0])) / 86400000))
  : 0;
```

Worth saying explicitly before it is implemented: **this moves figures in the
Aging Debtors report.** No total changes — the same money in the same accounts —
but adjusted accounts move out of the 0-day bucket into whatever bucket their
adjustment date puts them in, which for the Loglogo set is 60–90+ days. That is
the correction, but it will look like a jump in old debt the first time the
report is run afterwards, and whoever reads it should be told why.

> **Fixed 2026-09-16.** Implemented as prescribed: `daysOverdue` now anchors on
> the oldest of the oldest unpaid sale and the oldest debt-DEEPENING adjustment
> (`amount < 0` — a positive adjustment reduces debt and is not something to
> age). Dates are ISO, so the string sort is chronological, matching the
> comparison `adjustmentsFor` already sorts on. Accounts with neither anchor
> still report 0. Build and lint clean.
>
> The report's existing "Includes balance adjustments" notice now reads "...
> corrected to a figure the invoices do not show, **aged from the adjustment
> date**", so the reader is told where the age came from in the report itself
> rather than only in this document.
>
> ⚠ **THE NEXT AGING REPORT WILL LOOK DIFFERENT.** No total moves and no
> account gains or loses debt — the same money in the same accounts — but
> adjusted accounts leave the 0-day bucket for whatever their adjustment date
> puts them in, which for the Loglogo set is 60–90+ days. It will read as a
> jump in old debt. It is a correction of the age, not a change in the debt,
> and whoever receives that report should be told before they see it.
>
> **Not measured.** The before/after bucket figures need the live data, which
> this change did not have. Generate the report once before merging and once
> after, and keep both — that comparison is the evidence for the restatement.

### 4. The standing balance-reconciliation query is now two-term and false-positives — FIXED 2026-09-16

`migrations/README.md` designates `025`'s check 4 as the permanent control on
balance drift: *"Keep that query — once credit is in use it stops being an
equality and becomes the reconciliation between `customers.balance` and the
credit pool."*

`027` added a third term to the formula and **did not extend that query.** Its
own check 2 (`027:548`–`558`) is the same two-term shape, correctly labelled
*"NOTHING CHANGED YET"* for a point in time that has now passed.

A grep across `migrations/` and `docs/` finds **no three-term reconciliation
anywhere.** So the only query that can detect a balance disagreeing with its own
records now reports every adjusted customer as drift. In practice that means it
gets run, returns the Loglogo accounts, and is dismissed — which is the same as
not having it.

This matters more than it looks: balance drift is the recurring defect in this
system's history (`018` exists for it, `017` made the figure derived because of
it, and one account — id 97 — is still out by KES 2,520). Losing the detector
for it while adding a term to the formula is the wrong direction.

**Fix:** add the three-term version to `docs/` as the maintained control:

```sql
select c.id, c.name, c.balance,
       coalesce(s.unpaid, 0) + coalesce(p.credit, 0) + coalesce(a.adj, 0) as derived,
       c.balance - (coalesce(s.unpaid, 0) + coalesce(p.credit, 0) + coalesce(a.adj, 0)) as drift
  from customers c
  left join lateral (select -coalesce(sum(s.total - coalesce(s.paid, 0)), 0) as unpaid
                       from sales s where s."customerId" = c.id) s on true
  left join lateral (select coalesce(sum(p.amount), 0) as credit
                       from payments p
                      where p."customerId" = c.id and p."saleId" is null) p on true
  left join lateral (select coalesce(sum(a.amount), 0) as adj
                       from customer_adjustments a
                      where a."customerId" = c.id) a on true
 where c.balance is distinct from
       (coalesce(s.unpaid, 0) + coalesce(p.credit, 0) + coalesce(a.adj, 0));
```

Expect id 97 and nothing else. Anything new is a real defect.

> **Fixed 2026-09-16.** Landed as `docs/balance-reconciliation.sql`, a
> read-only file safe to run on production, with the query above verified
> term-by-term against `recompute_customer_balance` as `027` defines it
> (`027:246`-`027:310`): `-sum(total - paid)`, `sum(amount) where "saleId" is
> null`, `sum(amount)` over `customer_adjustments`. Two supporting blocks came
> with it — the negative-credit check carried forward from `025` check 5, and
> a listing of the adjustment rows, because a balance that looks wrong is often
> an adjustment nobody remembers posting and block A cannot say so on its own.
>
> `migrations/README.md` now designates that file as the standing control in
> place of `025` check 4, and the `025` row says so too — the designation was
> the half that made the old query authoritative.
>
> **RUN 2026-09-16 by the operator against production: it returned id 97 and
> nothing else,** which is exactly what this finding predicted. The control is
> therefore not merely published but verified against live data, and the
> three-term formula reconciles for every customer except the one account whose
> drift predates it. Anything this query returns from now on beyond id 97 is a
> real defect.
>
> **Blocks B and C were run the same day and also came back as expected.** B
> (negative credit) returned no rows, so nothing has written around
> `recompute_customer_balance`'s `v_credit < 0` guard. C listed the Loglogo
> corrections plus the adjustments posted since. Read against A, that is the
> useful pair: every account carrying an adjustment reconciles, so the third
> term is landing in the balance correctly rather than merely existing.
>
> The drift figure for id 97 was not captured. It is expected to be the
> standing KES 2,520 understatement; if it has moved, that is worth knowing,
> since nothing in this session touched it.

### 5. `027`'s header records a divergence in `025` that the file contradicts — FIXED 2026-09-16 (settled against production; there was no divergence)

`027:216`–`232` states, in capitals, that its section 2 was built on the live
function body and **not** on `025`, because *"THEY ARE NOT THE SAME"*. It lists
three things *"production carries and `025` does not"*:

* `perform 1 from customers where id = p_customer_id for update`
* `if not found then return null; end if;`
* `v_role := coalesce(get_my_role(), '')`

**All three are present in `migrations/025_on_account_credit.sql`** — at lines
`271`, `272` and `264` respectively, inside the real
`create or replace function recompute_customer_balance` at line `247`. `025` has
exactly one commit in its history (`d0a3d64`) and has never been amended, so it
contained all three when `027` was written.

Diffing the two function bodies with comments and blank lines stripped gives
five changed lines, and they are all the adjustment term:

```
> v_adjust numeric;                                    (declaration)
< update customers set balance = v_sales + v_credit …
> select coalesce(sum(a.amount), 0) into v_adjust …    (4 lines)
> update customers set balance = v_sales + v_credit + v_adjust …
```

**The code is correct either way** — section 2 is right, the lock is there, and
building on the live body was the right instinct. What is wrong is the record:
commit `7e63b9b` and the `027` header both assert a repo-vs-production
disagreement that is checkable and does not hold.

Two reasons this is worth correcting rather than shrugging at. First, it is a
standing invitation for someone to "resynchronise" `025` to a divergence that
does not exist. Second, and more useful: `027`'s pre-flight `0b` genuinely did
read something out of `pg_proc` that did not match what the author was comparing
it against. Whatever that was, it is now recorded as an answer instead of an open
question, so nobody will look again. **The live body should be read once more and
diffed against `025` properly.** If it matches, correct the header and the
README. If it does not, the difference is real, unidentified, and in the balance
function.

> **Partly fixed, 2026-09-16.** The repo half is settled and corrected. The
> three enumerated items are in `025` at `:264`, `:271` and `:272`, and diffing
> the two function bodies with comments and blank lines stripped gives exactly
> the five lines this finding predicted — `v_adjust`, its four-line select, and
> its term in the final UPDATE — with everything else identical. `027`'s
> section 2 header and its pre-flight check `0b` have both been corrected in

> 2026-09-02 read showed as UNKNOWN and name the query to settle it. That is
> the outcome this finding asked for: an answer nobody would question again is
> turned back into an open question somebody can close.

> **Closed the same day.** The operator ran the `prosrc` query against
> production and the result was diffed against the repo. The live body is
> **byte-identical** to `027` section 2 (same md5 once `prosrc`'s leading

## Verified sound

Traced and found correct. Recorded so the next audit need not re-derive it.

- **`027`'s client half is complete.** The migration header names the two places
  that rebuild a balance outside the database and warns they will silently
  disagree if not updated. Both were: the customer card ledger pushes adjustment
  rows with the sign in the right column (`7528`–`7539`) and explains why, and
  the statement PDF carries the adjustment line and its reason (`3062`–`3165`).
  The Debtors report goes further than required and surfaces
  `adjustmentsApplied` / `adjustedAccounts` (`1696`–`1699`) so a correction
  cannot become a quiet hole in the total.
- **`027`'s gates fail closed.** `record_customer_adjustment` and
  `delete_customer_adjustment` both use `v_role is distinct from 'admin'`
  (`027:379`, `452`), not `<>`, so a NULL role from a caller with no `profiles`
  row is refused. This is the documented past finding that `010` fell into, and
  the file names it in its own header before avoiding it.
- **`027` follows the RLS-in-the-same-file rule.** The table, `enable row level
  security`, and its policies are all in `027` (`172`, `496`, `499`), never a
  follow-up. `created_by` is stamped server-side from `auth.uid()`, so the
  ledger's attribution line for an adjustment is evidence rather than a claim.
- **The balance function kept its row lock through the `027` rewrite.** This was
  the real risk in that file — redefining the most-called money function to add
  a term is how a lock gets dropped by accident. It is present at `027:277`.
  (See finding 5 for the record-keeping around this, which is the only thing
  wrong here.)
- **`026` is wired correctly.** `assert_stock_not_negative` is called inside
  `record_production` (`026:258`) with a pinned `search_path` (`189`), closing
  the raw-material floor `020` deferred.
- **`visibleAdjustments` is scoped like `visibleCustomers`, deliberately**
  (`607`–`611`). Scoping it like `visibleSales` would hide adjustments from a
  sales user with no location while still showing them the customer and the
  balance, so their ledger would stop adding up. The reasoning is written down
  at the definition. RLS remains the boundary either way.
- **The delivery note's carton labelling is right.** `DOC_SIZE_LABELS` (`273`)
  relabels only `0.5L`, `1.5L` and `5L`, which are exactly the sizes with
  `BOTTLES_PER_CARTON` above 1 (24, 12, 4 at `356`). `18.9L` and both refills
  are single bottles and are correctly left alone. Screen labels are unchanged
  by design, which is why the customer card ledger still uses `SIZE_LABELS`
  (`7474`) — that is correct, not a missed site.
- **`dispatchedByName` (`812`) is honest about what it cannot know.** Profiles
  RLS gives a non-admin only their own row, so a manager printing someone else's
  sale gets `null` and the note rules a blank line rather than printing the name
  of whoever is at the screen. The delivery note also takes its dispatch date
  from `sale.date`, not today, so a reprint and a signed copy of the same
  delivery cannot disagree.
- **The delivery note states no money.** No unit prices, no totals, no balance —
  a goods document, with the footer pointing at the invoice for the amount due.
  Read-only; it changes no records.
