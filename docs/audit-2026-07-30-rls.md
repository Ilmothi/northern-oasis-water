applied.** The live database was treated as the source of truth throughout;
migration files were used only to explain what the live state *should* have been.

> been silently corrupting stock rather than only blocking it — finished goods

**Migration 010 was applied partially.** Sections 4/5/6 (policies) are live and
confirmed in block C. Sections 2/3 — which redefine `apply_inventory_deltas` and
`set_inventory_value` as SECURITY DEFINER with internal `get_my_role()` checks —
never applied. Block L confirms both are still 009's SECURITY INVOKER versions.

An INVOKER function's `UPDATE inventory_state` is policed by RLS, and 010's policy
section set that to **admin only**. So for manager and sales users the UPDATE matches
zero rows and the function raises `inventory_state row ... not found`.

This was masked until now by the blanket `"Authenticated full access"` (ALL/true/true)
policy on `inventory_state`. **Migration 013 dropped it**, making the admin-only
policy binding for the first time. 013's header asserts the inventory functions
"carry their own explicit role checks and are unaffected by this change" — true of
the migration file, false of the live database.

Current production impact, for every non-admin role:

- **Recording a sale fails completely.** `record_sale` (011) is atomic and calls
  `apply_inventory_deltas`, so the exception rolls back the whole transaction.
  `src/App.jsx:2937` surfaces *"Could not save this sale — nothing was recorded."*
- **Production logging and consignment delivery** fail the same way via
  `persistInventoryDeltas` (`src/App.jsx:498`), which returns `null` and triggers the
  "stock could not be updated" alert.
- Only an `admin` can move stock or record a sale.

The breakage holds whether or not the live bodies contain 010's internal role check:
a sales user would pass that check and still fail on the policy.

Note `proconfig` is identical between the 009 and 010 versions (`public, pg_temp`);
only `prosecdef` differs. That is why no casual dump caught it.

**Records to correct:** `migrations/README.md` lists 010 as fully applied on
2026-07-28. `docs/audit-2026-07-28.md` closes findings 5 and 10 on that basis. Both
are wrong; findings 5 and 10 are still open. Finding 5 has inverted —
`set_inventory_value` has no internal admin gate, so it is admin-only purely by table
policy, which is accidentally correct and will silently loosen if that policy changes.

## Added 2026-07-31 — found while fixing the URGENT item

Neither of these was visible on 2026-07-30. Both came out of applying 014.

### 14 — `SECURITY DEFINER` role gates fail OPEN on a null role

`get_my_role()` is `select role from profiles where id = auth.uid()`, so it
returns NULL for any caller with no `profiles` row. Inside plpgsql that inverts
the gate:

```sql
if get_my_role() not in ('admin','manager','sales') then  -- NULL, not TRUE
  raise exception '...';                                  -- never fires
end if;                                                   -- execution continues
```

`NULL not in (...)` and `NULL <> 'admin'` both evaluate to NULL, so `IF` does not
take the branch and the caller passes straight through the only check standing
between them and `inventory_state` — RLS having been bypassed by DEFINER.

Migration 010's header asserts both functions "fail closed". They fail open.

**Live exposure was minutes, not days.** Because 010 §2–3 had never applied, the
live functions were 009's INVOKER versions with no internal check at all, gated
by RLS. The fail-open body was briefly live on 2026-07-31 when §2 was applied on
its own, and was replaced within the same session. 014 ships
`coalesce(get_my_role(), '')` and `is distinct from` instead.

Scope note: this affects plpgsql `IF` only. The same expression in an RLS `USING`
clause is safe — NULL there denies the row — so 001's policies genuinely do fail
closed. **This compounds finding 5**: both of 014's gates call `get_my_role()`, so
the whole stock-write boundary now depends on a function whose `search_path` omits
`pg_temp`.

Two standing consequences:

- Any new `SECURITY DEFINER` function needs the null-safe comparison form.
- **A DEFINER role gate cannot be tested from the SQL Editor.** There is no JWT
  there, so `auth.uid()` is NULL and a *correct* gate refuses everything. Success
  in the editor means the gate is broken. Test as a real logged-in user.

### 15 — the outage corrupted stock, it did not merely block it

The 2026-07-30 write-up describes the production-logging failure as a half-post.
It is worse than that in effect. Admin-recorded sales deducted finished goods
successfully throughout, while non-admin production runs recorded their logs and
never credited the cartons. Live values on 2026-07-31, read from
`inventory_state`:

```
finishedGoods 0.5L   -24 cartons
finishedGoods 1.5L  -110 cartons
```

Negative finished goods means cartons were sold that the system has no record of
producing. Raw materials are the mirror image and are overstated, since the same
runs consumed bottles, labels and stamps that were never deducted.

014 stops the bleeding and 015 makes the half-post structurally impossible, but
neither repairs the existing figures. `docs/production-stock-reconciliation.sql`
computes the correction; it is read-only and the corrections go through the Stock
Adjustments tab so they carry an audit row. **Still outstanding as of
2026-07-31.** Expect P&L COGS and closing stock value to move when it is applied —
that is the discrepancy leaving the books.

The same half-posting shape exists in `handleConsignDeliver` and
`handleConsignReturn` (`src/App.jsx`), which 015 does **not** cover. Block 4 of the
reconciliation script quantifies it.

## Answers to the six audit questions

1. **Helper functions.** Both SECURITY DEFINER, both pinned, both to the *unsafe*
   form omitting `pg_temp`. Live matches 001. Finding 5.
2. **INSERT `with_check`.** Three too permissive: `payments_insert`,
   `sales_insert_non_admin`, and `customers_insert`'s null-location branch
   (findings 2, 3, 12). All others properly role-gated.
   `production_logs_insert` is the one policy that gets attribution right
   (`role='sales' AND created_by = auth.uid()`) and is the pattern the others need.
3. **`finished_goods` / `raw_materials`.** Queried nowhere. The app uses
   `inventory_state` with JSONB rows keyed `'rawMaterials'`/`'finishedGoods'` —
   different objects entirely. RLS on, zero policies. Row counts still unknown.
4. **`cost_settings` / `inventory_state`.** `inventory_state` read is correct as-is;
   all roles need stock levels and it is fetched unconditionally. `cost_settings` is
   genuinely needed by admin and manager; sales receives it only as a side effect of
   the same unconditional fetch (`src/App.jsx:591`), and it is margin data.
5. **`profiles`.** Role and location are assigned by `handle_new_user` running as
   owner, plus manual dashboard edits. There is **no admin screen at all** —
   `profiles` appears once in 7,431 lines, a SELECT at `src/App.jsx:353`. Nothing is
   silently failing because no such code exists. `const role = userProfile?.role ||
   'sales'` (`src/App.jsx:421`) fails closed to least privilege. The real gap is
   operational: no in-app way to change a role, offboard a user, or fix a location.
6. **Frontend-enforced, database-permitted.** Findings 7, 8, 9 for reads. The
   read-side client filters (`visibleSales`/`visiblePayments`/`visibleCustomers`,
   `src/App.jsx:437-455`) *are* properly backstopped by RLS since 013 — that part
   worked. The write side is not: findings 1, 2 and 3 are all "no button exists, so
   no policy was written."
