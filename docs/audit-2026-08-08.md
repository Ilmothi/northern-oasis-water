Northern Water Company Ltd (OASIS Springs) business management system.

**Scope.** Everything on `main` since the 2026-07-30 RLS audit: migrations `017`
through `021`, the client changes in PRs #31–#33, and a re-check of the items
left open by `docs/audit-2026-07-28.md` and `docs/audit-2026-07-30-rls.md`.
Line references are against `1fecdaa`.

**Baseline health.** `npm run build` and `npm run lint` both pass clean.

**Method note.** This audit did something the previous two did not: it probed the
live database read-only to settle whether `019`–`021` actually applied, rather

**Status key.** OPEN = needs work. RESOLVED = settled by this audit, no code

## High

### 1. Payroll is the last money path with no double-submit guard — OPEN

PR #33 fixed duplicate sales, payments and production runs. It put the guard on
the modal's Save button (`src/App.jsx:7456`), which was the right call — nine
handlers funnel through it and all nine are covered.

**Both payroll paths sit outside that modal and are therefore uncovered:**

- `recordSalaryPayment` (`888`), fired by a plain button at `6273`
- `recordCasualPayment` (`930`), fired by a plain button at `6345`

Neither is wrapped in `runSave` (`543`), neither is wrapped in `withTimeout`
(`560`), neither button carries a `disabled` attribute, and neither record type
carries a `client_key`. Every layer of the PR #33 fix is absent here.

The salary path looks protected but is not. `isSalaryPaid` (`882`) reads
`payrollPayments` — local state that is only updated at `924`, *after* the write
returns. Two taps land two handlers before either completes, both read the same
stale state, both pass the check, and both write. There is **no unique
constraint on `payroll_payments` anywhere in `migrations/`** to catch it at the
database, so nothing downstream refuses the second row.

**The failure mode actively invites the duplicate.** `recordSalaryPayment` is
two sequential writes with no transaction: the Salary expense at `910`, then the
payroll row at `917`. If the second fails, the expense is already committed and
the user is told *"Expense saved but the payroll record failed"* (`921`) — and
because no payroll row exists, `isSalaryPaid` returns false and the UI shows
**"Record Payment" again**. An operator who retries produces a second Salary
expense in the P&L for a salary paid once.

`recordCasualPayment` has the same shape over more steps — one expense, N
payroll rows, then a loop of N `production_logs` updates (`984`) — and its own
code already acknowledges the exposure, alerting *"Do NOT record a second payout
for this range"* (`993`).

**Impact:** duplicated Salary and Casual Labour expenses inflate operating costs
in the P&L, and duplicated `payroll_payments` rows misstate what staff were
actually paid. This is the same class of defect PR #33 was raised to fix, on the
one path where a single duplicate is worth a whole payroll run.

**Suggested fix, in order of value:**

1. A unique index on `payroll_payments (type, employee_id, period_label)` —
   this is the real enforcement, and it is what `021` did for the money paths.
   Casual rows would need a period key that is stable per payout range.
2. Route both handlers through `runSave` and `withTimeout`, as PR #33 did for
   the modal.
3. Make each an atomic RPC, following `015`/`016`. This is the pattern the rest
   of the money paths already use and the only thing that closes the
   half-committed expense.

## Medium

### 2. `020` applying does NOT prove the stock reconciliation was run — OPEN

`migrations/README.md`, `docs/audit-2026-07-30-rls.md` (finding 15) and the
project notes all record the finished-goods reconciliation (0.5 L −24 cartons,
1.5 L −110 cartons) as **still outstanding**.

`020` is wrapped `begin;` (`110`) … `commit;` (`315`), and its Section 0
(`114`–`135`) raises and aborts if finished goods are negative — *before*
Section 1 creates `assert_stock_not_negative` at `143`. So the probe result
above is load-bearing: **the function exists, therefore Section 0 passed,
therefore finished goods were non-negative on 2026-08-04.**

That is where it stops. There are two ways stock got back above zero, and they
have very different consequences:

- **The reconciliation was run** and simply never recorded in the README or the
  audit docs. Books are correct; only the paperwork is stale.
- **Ordinary production absorbed it.** Between 2026-08-01 and 2026-08-04,
  production runs credited enough cartons to lift −24 and −110 back above zero
  on their own. In that case the drift was never corrected — it was *buried*.
  The phantom stock is now silently baked into finished goods, and every closing
  stock value and P&L COGS figure since carries it.

The second is the more likely reading, since three separate records all still
say the correction is outstanding and none of them mention it being done.

**This is a bookkeeping question, not a code one, and it is cheap to settle:**
check `stock_adjustments` for rows dated 2026-08-01 to 2026-08-04 covering 0.5 L
and 1.5 L. Reconciliation goes through the Stock Adjustments tab precisely so it
leaves an audit row. If those rows exist, update the records. If they do not,
the drift is still in the books and `docs/production-stock-reconciliation.sql`
still needs to run — against current figures, not the ones from 2026-07-31.

### 3. The non-atomic remainder is now the whole of the residual duplicate risk — OPEN

`021` closed the lost-response duplicate for sales, payments and production.
What it deliberately did not cover (`021:99–101`) plus what PR #33 did not wrap
leaves an uneven surface. Current state:

| Path | Double-tap guard | Timeout | Idempotency key | Atomic |
|---|---|---|---|---|
| Sale, payment, production | ✅ | ✅ | ✅ | ✅ |
| Purchase, expense, customer | ✅ | ✅ | ❌ | ❌ |
| Consignment (4 actions) | ✅ | ❌ | ❌ | ✅ (`011`/`016`) |
| Stock adjustment, employee | ✅ | ❌ | ❌ | ❌ |
| **Payroll (salary, casual)** | **❌** | **❌** | **❌** | **❌** |
| Cost settings, casual rate | ❌ | ❌ | n/a | n/a |

Two things worth pulling out of that table:

- **Consignment has no timeout.** `handleConsignDeliver` (`3118`),
  `handleConsignReturn` (`3167`), `handleConsignReportSold` (`3216`) and
  `handleConsignReconcile` (`3286`) all call their RPC unwrapped, so a dropped
  connection still hangs indefinitely — the exact condition PR #33 identified as
  the cause of field duplicates. The operations are atomic, so a duplicate here
  is a clean second posting rather than a corrupt one, but Report Sold posts a
  sale and moves a customer balance. Wrapping these four is a small change.
- **Purchases now fail differently, not better.** On timeout `handleSavePurchase`
  returns before adjusting raw materials (`1217`, `1267`). If the write did
  commit, the purchase exists and stock was never raised. The message is honest
  about the uncertainty, but the reconciliation burden is real and lands on
  whoever reads it.

Cost settings and the casual rate are unguarded but are idempotent updates, not
inserts — a double-tap writes the same value twice. Low priority.

### 4. `019` is unverified, and the branch fixing its verification query is unmerged — OPEN

`019` is the one migration of the recent three that the live probe cannot reach:
it adds no function and no column, only a modified `delete_payment`, a restored
`sales_insert_non_admin` policy, and a profile-location normalisation.

Its own verification block is known to be wrong. Branch
`fix-019-verification-query` (`8747622`, pushed, **never merged**) corrects
check 2 from `ilike '%for update%'` to `ilike '%p_payment_id for update%'` —
the original matches the explanatory comment inside the function body, since
`pg_get_functiondef` returns comments as well as code, so it reports
`still_locks = t` against a *correctly* applied function.

So the situation is: the migration is unverified, the query written to verify it
gives a false alarm, and the fix for that query is sitting on an unmerged
branch. **Merge `fix-019-verification-query`, then run the corrected block.**

`019` matters more than its size suggests — it is what restores payment
deletion, which has been broken since `013` (see the README's *017 aftermath*).
If it did not fully apply, nobody can delete a payment and the symptom is
silent: RLS refusals match zero rows rather than raising.

## Verified sound

Traced and found correct. Recorded so the next audit need not re-derive it.

- **The four-way `record_sale` chain is cumulative, not clobbering.** `record_sale`
  is redefined in `017`, `019`, `020` and `021` — a real risk, since the
  last-applied definition silently wins and could drop the earlier ones' logic.
  `021`'s final version (`231`–`318`) carries all four: `recompute_customer_balance`
  from `017`, server-side `auth.uid()` stamping from `019`, `assert_stock_not_negative`
  from `020`, and its own `client_key` replay. Nothing was lost.
- **The `021` replay design is right.** The partial unique index is the
  enforcement and the `SELECT` is only a fast path; the concurrent case is caught
  as `unique_violation` inside a sub-block and converted to the same replay
  response, so the transaction is not discarded. Validation is deliberately
  skipped on replay, which is correct — a resend of a committed sale must not be
  re-judged against rules or balances that have moved since.
- **The double-tap guard is correctly ref-based, not state-based.** `savingRef`
  (`355`) is what refuses the second call; `saving` only renders the label. State
  would not have re-rendered in time.
- **`handleSaveConsignment` (`3350`) returns each handler's promise** rather than
  calling it fire-and-forget, so `runSave` genuinely awaits the consignment
  actions. Had it not, the guard would have released immediately and covered
  nothing.
- **All three keyed paths handle replay consistently** — `clientKey` generated at
  form open (`2934`, `3369`, `3470`), `upsertById` (`616`) used on the response so
  a replayed row replaces rather than appends, and a `data.replayed` alert naming
  the existing record.
- **The `randomUUID` fallback is v4-shaped** and correctly sets the version and
  variant bits (`602`) — the column is `uuid` and would reject a malformed value.
- **Consignment half-posting is closed.** RLS finding 15 flagged
  `handleConsignDeliver`/`handleConsignReturn` as uncovered by `015`; `016`'s
  `consignment_move_stock` covers them and the client calls it (`3138`, `3185`).
