Northern Water Company Ltd (OASIS Springs) business management system.

**Scope.** The 1,475 changed lines in `src/App.jsx` since the previous audit

**Status key.** FIXED = corrected on branch `audit-fixes-2026-07-28`.

## High

### 1. Normal sale to a consignment shop double-deducts stock and double-books revenue — FIXED

The New Sale customer picker (`src/App.jsx:6722`) listed every customer with no
`is_consignee` exclusion or warning. `is_consignee` was read only by the
Consignment tab (`3004`) and the customer form (`7231`).

Recording an ordinary sale against a consignment shop deducted finished goods a
second time — the cartons already left the plant at delivery (`3076`) — and when
the shop later reported the same cartons through Report Sold, revenue and COGS
were counted twice. Nothing in the UI prevented it and the operation looked
entirely normal.

**Decision (owner, 2026-07-28):** consignment shops never buy stock outright, so
they are blocked rather than warned.

**Fix.** Consignment shops are excluded from the New Sale picker via a single
`saleCustomerOptions()` helper (used by both the list and its empty state, which
previously duplicated the filter), an explanatory note points staff to Report
Sold, and `handleSaveSale` rejects a consignee on save in case a shop is flagged
while the form is open.

### 2. `cogs`-tagged expenses silently dropped from the P&L — FIXED

`generateProfitLossReport` accumulated `cogsExpenses` and `excludedExpenses`
(`1447–1450`) and returned them (`1468–1469`), but `netProfit` excluded them
(`1454`) and **neither value was rendered** — not on screen (`4870–4887`) nor in
the printable statement (`2059–2064`). They were dead data.

Consequence: the P&L could not be reconciled against the Expense Report, which
does show those buckets (`1384–1385`). That breaches the standing rule that
reports must reconcile with underlying transaction records.

**Decision (owner, 2026-07-28):** the carton costs entered in Cost Settings
already include excise duty and material costs, so deducting these expenses again
would double-count. Net profit is correct as it stands.

**Fix.** A "Recorded, not deducted" memo block now appears on both the on-screen
and printable P&L, broken down by expense type so it ties line-for-line to the
Expense Report, with a note explaining why the amounts are not deducted. Net
profit, gross profit and both margins are unchanged — this is a disclosure fix,
not a maths change.

### 3. Non-atomic customer balance updates — OPEN

Carried over from 2026-06-29 and now in three places, not one: `2991` (sale),
`3217` (consignment report-sold), `3294` (consignment reconcile). Each does a
read-modify-write on `customers.balance` and only `console.error`s on failure, so
a failed update leaves a customer's debt silently wrong with no user-visible
signal. Two concurrent writes can still lose one.

Reconcile is the worst placement, since that is the path that *reduces* debt.

Fix requires the Phase 2 transactional RPCs (same pattern as
`009_atomic_inventory.sql`: move the read-modify-write server-side under a row
lock).

### 10. Sales-role users never deduct finished goods — MIGRATION DRAFTED

Found while drafting the fix for findings 4 and 5, so it is numbered out of
order.

`persistInventoryDeltas` (`491`) calls `apply_inventory_deltas`, which migration
009 declared `SECURITY INVOKER`. Its effective gate is therefore
`inventory_state_update`, which allows `('admin','manager')` only
(`001_rls_policies.sql:379–381`). Every sale deducts finished goods through that
function (`3019`).

So for a **sales-role** user: the sale row saves, the stock deduction is refused,
and the app shows "The sale was recorded, but the finished-goods stock could not
be updated. Please run a stock adjustment or reload." (`3024`) — on every sale.
Finished goods drift high by the full volume of every sale a sales user has ever
recorded.

The error handling is honest, so this is visible to whoever is using the app
rather than silent. **How much stock has actually drifted depends on whether
sales-role users have been recording sales in production** — that needs checking
against real usage, and it affects the recount already required by 009.

**Fix** in `migrations/010_inventory_and_consignment_authz.sql`:
`apply_inventory_deltas` becomes `SECURITY DEFINER` with an explicit
`admin/manager/sales` check, so the everyday delta path works for sales users
while the absolute-write path stays admin-only.

## Medium

### 4. Reconcile is admin-only in the UI but manager-capable in RLS — MIGRATION DRAFTED

The Reconcile button is gated `role === 'admin'` (`4408`), but
`consignment_movements_insert` allows `('admin','manager')`
(`migrations/008_consignment.sql:84–86`) and managers can insert into `sales`. A
manager calling the API directly can post credit notes that erase customer debt.

Per the project rule that RLS is the security boundary and UI role checks are
convenience only, this needs a policy split.

**Fix** in `migrations/010_inventory_and_consignment_authz.sql`: two permissive
INSERT policies — admins may insert any movement type, managers everything except
`'reconcile'`. Blocking the ledger half alone would have been cosmetic, since a
manager could post the credit note by itself and still wipe the debt, so
negative-total sales are restricted to admin in the same migration.

### 5. `set_inventory_value` lets a manager overwrite absolute stock — MIGRATION DRAFTED

Migration 009's header claims the RPC is "admin-gated in the UI and by
`inventory_state` RLS" (`009:28–29`, `147–149`), but `inventory_state_update`
allows `('admin','manager')` (`001_rls_policies.sql:379–381`).

Stock Adjustments are admin-only by design (nav `3874`) and the UI path correctly
writes a `stock_adjustments` audit record before touching stock (`1047`). A
manager calling the RPC directly skips that record entirely. The comment in 009
is wrong as written and should not be trusted until the policy is tightened.

**Fix** in `migrations/010_inventory_and_consignment_authz.sql`:
`set_inventory_value` becomes `SECURITY DEFINER` with an explicit
`get_my_role() = 'admin'` check, and direct INSERT/UPDATE on `inventory_state`
drops to admin-only — safe because the app no longer writes that table directly
(`588` is the only reference and it is a SELECT), which also removes the
"overwrite the whole blob by hand" path that 009 set out to close.

Caveat recorded in the migration: a manager can still UPDATE `customers.balance`
directly via `customers_update_admin_manager`, so debt can be altered without an
audit trail. That is finding 3's Phase 2 work and is out of scope for 010.

### 6. Consignment stock is invisible in asset valuation — FIXED

`calculateFinishedGoodsValue` (`673`) read only `state.finishedGoods`, so cartons
sitting unsold at shops — still company assets — disappeared from "Total Assets"
in the header (`3835`) and in Cost Settings (`6074`) the moment they were
delivered. The understatement grew with consignment volume.

**Fix** (branch `consignment-stock-valuation`): a new
`calculateConsignmentStockValue()` values the movement ledger's on-hand cartons
at the same carton cost, and `calculateTotalAssets()` becomes the single source
for the headline figure so the dashboard header and the Cost Settings panel
cannot drift apart. Cost Settings now lists plant stock and consignment stock as
separate lines, with a note explaining why off-site stock counts as an asset;
both consignment rows are hidden entirely when no consignment shops exist.

**This raises the displayed Total Assets figure** by the value of stock currently
at shops — that is the point of the fix, and the previous figure was
understated. No report changes: P&L COGS derives from sales, and Cash Collected
and Debtors never referenced these helpers.

### 7. Production tab offered to sales role but blocked by RLS — OPEN

Nav grants `production` to `['admin','manager','sales']` (`3870`), while
`production_logs` SELECT and INSERT are admin/manager only (`001:291–297`), and
`inventory_state` UPDATE excludes sales too. A sales user sees an empty log list
and gets a hard error on save.

No corruption risk — `handleSaveProduction` checks the insert and aborts cleanly
(`3596–3600`) — but CLAUDE.md lists production logging as a sales-role
capability, so either the RLS policies or the nav + documentation are wrong. This
needs an owner decision on intent before either side is changed.

## Verified sound

Traced and found correct, recorded here so future audits need not re-derive it:

- **Consignment accounting reconciles.** deliver → reconcile → report-sold
  recognises COGS exactly once, and plant finished goods are deducted exactly
  once. The negative-quantity credit note (`3253`) correctly reverses both
  revenue and the COGS of the originally mis-booked sale.
- **Persist-first ordering is consistent** across delivery, return, report-sold,
  reconcile, production, and purchase edits. Every write result is checked and
  surfaced with a specific, honest alert rather than a generic success.
- **`handleDeleteSale` refuses consignment-linked sales** (`2682`) with an
  accurate explanation, preventing the stock-inflating reversal.
- **Migration 009's delta design is sound** — single locking `UPDATE` per change,
  `SECURITY INVOKER` so RLS still governs, absolute writes kept on a separate
  admin path.
- **Stock-count correction is blocked when inventory never loaded** (`1011`),
  closing the demo-defaults-overwrite hole.
- **Cash Collected avoids double-counting** point-of-sale cash against linked
  payment records (`1319–1323`).
- **Demo seed data leak (2026-06-29) confirmed fixed** — state now replaces on
  any successful fetch (`522–530`).
